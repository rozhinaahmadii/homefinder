# Homefinder

Real estate listings app (Polish market, ~100 listings). Take-home exercise: improve product, technical state, and add AI functionality. Time-boxed, so scope discipline matters more than completeness.

## Goals, in priority order

1. Trustworthy data: raw listings are validated, normalized, deduplicated and flagged at ingest.
2. Forgiving search: diacritic-insensitive, multi-term, feature filters, sorting, sale/rent-aware price.
3. Assistant: natural-language request -> agent returns a shortlist of listing IDs with reasoning and data warnings.
4. MCP server exposing the same tools the agent uses.
5. Evals for the agent, unit tests for normalization and search.

## Commands

```bash
npm run dev      # web (Vite) + API (Hono on port 3001), started together
npm run ingest   # data/listings.raw.json -> data/homefinder.db
npm run test     # vitest
npm run eval     # agent scenarios, prints pass rate (needs API key)
npm run mcp      # MCP server over stdio
npm run check    # typecheck + test; must pass before every commit
```

Update this section whenever a script is added or renamed.

Environment: Windows, PowerShell, Node 24. Use commands that work in PowerShell.

## Architecture

```
data/listings.raw.json   original data, never edited by hand or by code
data/homefinder.db       generated by ingest, gitignored
scripts/                 audit.ts (read-only report), ingest.ts (raw -> SQLite)
src/                     frontend: vanilla TS views, talks to the API only
src/core/                pure shared logic: types, normalize, dedupe, search (no I/O)
server/                  db.ts, api.ts, tools.ts, mcp.ts, agent.ts
evals/                   scenarios.json + run.ts
docs/                    DECISIONS.md, DATA_AUDIT.md, AI_LOG.md
```

Data flow: raw JSON -> ingest (validate, normalize, flag, dedupe) -> SQLite -> src/core/search -> API, MCP server and agent.

Rules that hold the design together:

- One search implementation in `src/core/search.ts`. The API, the MCP server and the agent all call it. Never add a second filtering path, including in the browser.
- Only `server/db.ts` contains SQL.
- Tools are defined once in `server/tools.ts` (name, description, Zod schema, handler). The MCP server and the agent both register from that list.
- The agent returns listing IDs and reasoning only. The UI renders prices, areas and other facts from the store, never from model output.
- The app must work with no API key. The assistant is an enhancement.
- `server/mcp.ts` must never write to stdout except protocol messages. Log to stderr.

## Data rules

- Normalization is deterministic. No LLM calls in ingest.
- Fix only what is unambiguous: casing, whitespace, units, number formats, enum synonyms, date formats, feature synonyms and translations.
- Never guess a value. If a field is implausible or contradicts the description, keep the raw value and add a quality flag.
- Flag detection never changes a value.
- Every normalization rule has a test using a real dirty value from the raw file.
- Duplicates are marked with `duplicateOf`, not deleted.

## Conventions

- TypeScript strict. No `any`, no type casts on external data; parse with Zod at boundaries (raw data, API query params, tool inputs).
- `src/core` stays pure and framework-free.
- Small functions, plain names, no comments restating the code.
- No new dependency without a line in docs/DECISIONS.md saying why.
- Keep the frontend vanilla. Do not introduce a UI framework.
- Never render "undefined", "NaN" or "null" to the user.

## Out of scope (do not build, even if it seems helpful)

Auth, favourites, maps, pagination, embeddings or vector search, multi-agent setups, agent frameworks, an ORM, Postgres, Docker, currency conversion, UI framework migration.

If a task seems to need one of these, stop and ask.

## How to work in this repo

- Propose a plan before changing more than one file.
- One concern per change. Do not refactor unrelated code in passing.
- After each change run `npm run check` and report the result.
- When a decision is made or changed, add or update the entry in docs/DECISIONS.md. Do not add entries for decisions the user has not made.
- Do not edit expected values in evals/scenarios.json without asking.
- When library code does not compile, check the installed version in node_modules for the current API instead of guessing.
- When unsure about a product or scope decision, ask instead of choosing.

## Definition of done

- `npm run check` passes.
- New behaviour has a test, or an eval scenario if it is agent behaviour.
- README and this file still describe reality.
